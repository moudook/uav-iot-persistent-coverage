# UAV-IoT Persistent Coverage — Working Implementation

Executable implementation of **"Persistent and Fault-Tolerant UAV-IoT Coverage:
A Multi-Agent Reinforcement Learning Framework for Joint Coverage, Connectivity,
and Energy Management"** (`../Mlawn-midsem-tex.tex`).

Everything below runs and produces numbers. The numbers in the paper are
regenerated by one command, and every quantitative claim in the paper is
recomputed by an automated audit.

---

## Quick start

```powershell
cd Project1\ml_impl
python tests\run_tests.py        # the test suite
python analysis\claim_audit.py   # every checkable claim in the paper
python run_all.py                # the whole experiment matrix (~13 h)
python run_all.py --stage obs    # just the observation A/B/C

```

`uav_wireless/experiments.py :: base_config()`. Every script builds from it,
so the numbers in the paper, the CSVs and the claim audit all describe the
same experiment.

## The measurement protocol

Every number in the paper is produced under one protocol, and this is the
protocol:

1. **Training**: 25 episodes x 2000 steps per training run. The base
   comparison trains **5** runs, the component ablation and the observation
   arms **3**, the learned baselines 3, the energy and credit arms 3.
2. **Evaluation**: 5 scenes per policy. A controller's row is the mean over
   its **training** runs, and the reported spread is the seed-to-seed
   spread of those runs. The rule baselines are deterministic, so their
   spread is over the evaluation scenes.
3. **The number of evaluation scenes is part of the protocol**, and a run
   with three instead of five is a different measurement: a per-seed row is
   the mean over the evaluation scenes, so it changes. This is not a
   formality -- a re-run that omitted `--eval-seeds 5` looked like a
   reproducibility violation, and `analysis/repro_probe.py` and
   `analysis/train_repro_probe.py` showed that the training and the
   evaluation are both deterministic. Always pass the whole protocol.
4. **The device and the thread count are part of the protocol** too. The
   floating-point kernels differ between the CPU and the GPU, and the order
   of the reductions differs with the thread count, so two runs of the same
   configuration that land on different devices are not the same
   experiment. `UAV_DEVICE` defaults to the CPU, the thread count is
   pinned in `train.py`, and every artefact records the device it was
   measured on. The same seed on the GPU and on the CPU gives different
   weights (about 6e-4 apart after one episode), and it compounds through
   the updates.
5. **The evaluation is seeded** (`uav_wireless/seeding.py`). The deployed
   policy *samples*, and the sampling draws from the global torch RNG. If
   that RNG is not seeded, an evaluation is a fresh random draw every time
   it is run: the same policy file, evaluated three times on the same five
   scenes, gave CK 0.734, 0.701 and 0.671, with the same standard deviation
   to four decimals. The seed is derived from the evaluation seed **alone**,
   so every controller sees the same stream on the same scene (common
   random numbers) and a comparison between controllers is a comparison
   between policies rather than between the luck of the draw.
6. **The ablation is paired.** The variants share the training seeds, so a
   difference is measured on the same training runs; the table reports the
   paired difference and the seed-to-seed spread.
7. **The ablation uses the base comparison's budget**, so its "Full" row is
   the same experiment as the base comparison's MAPPO row. The cross-table
   check in `analysis/final_checks.py` verifies that the observation arm C,
   the credit arm A, the energy arm A and the ablation's full row agree
   **to the digit**, because they are one experiment.
8. Every training run's policy is **saved** (`mappo_base_s{seed}.pt`), so
   every number can be recomputed from a stored artefact.

## The canonical configuration, and why each choice was made

| Choice | Value | Why |
|---|---|---|
| Fleet size | `N = 8` | The corner-packing bound requires `N >= 4K`; `N = 5, K = 2` is provably infeasible. |
| Coverage target | `K = 2`, `R_cov = 35 m` | The report's values, on the corrected feasible fleet. |
| Initial deployment | **connected cluster in one corner** | A centred ring already covers 17 of 20 sensors at `t=0`, so every controller — including one that never moves — scores `CK = 0.850` and the comparison cannot separate them. The ring is kept as scenario **S9**. |
| Episode length | **2000 steps (400 s)** | At 400 steps the pack never depletes, so the return-to-charge transition never fires, the charging arbitration is never entered and the reserve UAV has nothing to recover. |

| Observation | identity + `4x4` coverage map + pad bearing | See *What the observation must contain* below. |

## What the observation must contain

Three separate defects, each of which blocks the shared policy from working
at all, and each of which the paper's own argument for parameter sharing
already requires:

1. **No identity.** Foerster et al. justify parameter sharing by requiring
   that each agent's own observation identify it. Eq. (4) did not, so in a
   symmetric deployment every agent received an almost identical input, the
   deterministic policy selected the same action for all of them, and the
   swarm translated as a rigid body. Measured: **1.00 distinct actions out
   of 8**, swarm spread frozen at its initial value.
   → `use_agent_id=True` appends a one-hot identity of length `N`.
2. **No indication of where the deficit is.** The agent knew *how many*
   sensors it covered but not *which* were under-covered, so nothing in the
   observation pointed towards the deficit.
   → `map_grid=4` appends a `4x4` summary of the share of under-covered
   sensors per cell. The infrastructure that owns the charging pads also
   aggregates the IoT service reports, so this is a communication assumption
   rather than an oracle, and the encoding is fixed size: the observation
   does not grow with `M` (tested for `M` in {10, 20, 40}).
3. **No way to express a return.** The observation carried the *energy* cost
   of the flight to a charging pad but not its direction.
   → `use_pad_bearing=True` appends the unit bearing and range to the
   nearest pad.

`analysis/ab_observation.py` compares the three configurations under
identical seeds, budget and evaluation seeds.

## Defects found and fixed (all with tests)

The most important ones, in order of severity:

| # | Defect | Consequence |
|---|---|---|
| 1 | **The simulator was static.** The motion step applied a move only when `np.all(action_mask(i))` was true — i.e. when *every* action including `A_CHARGE` was feasible. `A_CHARGE` is almost never feasible, so **no UAV ever moved**. | Coverage could not change; every controller scored identically; the action mask, the H-step lookahead and the articulation check were exercised on a static swarm. Every result measured before this fix was invalid. |
| 2 | **The energy state machine did not exist.** The environment never made the serve → return transition; only the rule-based baselines did it themselves. | A learned policy could not charge at all; the charging arbitration and the reserve mechanism were never exercised. |
| 3 | **Charging was uneconomic.** A charging UAV was billed the full hover power, so the pack lost more to the rotors than the pad put back. | No UAV could ever recover. |
| 4 | **An empty pack still counted as serving.** | A dead UAV provided coverage and connectivity. |
| 5 | **The battery never bound.** At 400 steps the swarm spent 13% of the pack. | The return state never fired. |
| 6 | **Baselines ignored their seed.** `baseline_fixed/greedy/reactive` accepted a `seed` argument and never applied it. | The "five seeds" of the base comparison ran the *same* scene five times for the baselines while the learned policy saw five different scenes. |
| 7 | **The time limit was reported as a termination.** | The GAE recursion bootstrapped from zero at *every* episode boundary, biasing every value target downward (Pardo et al., ICML 2018). |
| 8 | **The returns were formed from an untruncated advantage array.** | A shape mismatch whenever an episode ended early. |
| 9 | **The observation carried no agent identity.** | 1.00-1.8 distinct actions out of 8 under the argmax policy; the swarm barely dispersed. |
| 10 | **MAPPO's value normalisation was missing** although the report asserted it. | The report claimed a component the code did not have. |
| 11 | **The observation could not express a return** -- it carried the *energy* cost of the flight to a pad but not its direction. | A learned policy could not fly home. |
| 12 | **The observation did not say where the deficit was.** | No gradient signal for deployment at all. |
| 13 | The centred-ring start pre-solved the task. | The achievable range was `[0.9, 1.0]`, so nothing could be separated. |
| 14 | Reward eq. (23) negated only `U_t`. | Energy burn, partitions and motion were *rewarded*. |
| 15 | `snr_to_rate` off-by-one plus a floor. | The PHY gate was vacuous. |
| 16 | Path-loss exponent was additive. | LoS/NLoS were erased. |
| 17 | Noise power: dBm treated as watts. | A 30 dB error. |
| 18 | Shadowing drawn from the global RNG. | Non-reciprocal and non-reproducible links. |
| 19 | `local_obs` neighbour stride 2 with 4 fields per slot. | Neighbour 3 overwrote the neighbour count; the actor was trained on a corrupted observation. |
| 20 | `STATE_DIM = 80` hardcoded. | Valid only for `N = 5`. |
| 21 | `run_scenarios` passed `seed=0` over the config's own seed and evaluated only the first variant of each scenario. | Two of the scenario columns were wrong. |
| 22 | 41 communication-graph computations per step. | 13.2 ms/step -> 8.4 ms/step once the base graph was shared and the prospective graph was spliced (exactly, not approximately: the shadowing table is symmetric, and a test asserts the equivalence). |
| 23 | **The evaluation of a sampled policy was an uncontrolled random draw.** Eq. (13) specifies that the deployed policy samples, and `mappo.py` drew from the global torch RNG, which `eval_agent` never seeded. | The paper's numbers could not be reproduced from the stored artefact, and a comparison between two controllers carried an unquantified sampling component. Fixed by `uav_wireless/seeding.py`; pinned by five tests and by claim-audit item R1. |
| 24 | **The component ablation trained ONE seed per variant at 10 episodes**, while the base comparison trained five seeds at 25. | Its differences mixed the component with the training budget, and its spread was unmeasurable. It also disagreed with the observation arms, which said the full configuration was no better than the bare one. Now: the base comparison's seed count and budget, and the differences are paired. |
| 25 | **The main table's learned row was ONE policy while the text claimed five training seeds.** | The table and the text described different experiments. The row is now the mean over the five runs with the seed-to-seed spread, and every run's policy is saved. |

### The diagnosis the framework produced

The corrected simulator revealed that the learned controller was stranding
**all eight** UAVs in nearly every episode, while the reactive heuristic
stranded 0.7.  That looked like a catastrophic energy-management failure.
The obvious reading was that the controller had failed at energy
management, and the obvious fix was a reward term that prices the
consequence of an empty pack.  `analysis/ab_energy_management.py` tested
that reading with four controlled arms, each differing in one respect:

- **A** the proposed configuration;
- **B** a pack ten times the nominal size, so that no UAV can strand at
  all;
- **C** without the threshold-violation reward term;
- **D** under the earlier energy rule of the safety filter, which admitted
  a departure with a flat battery.

All four land inside the seed-to-seed spread of the learner, so the energy
model is **not** what limits the controller.  What the earlier rule did
was strand seven of the eight UAVs per episode, against one for the
corrected rule: a real defect in the safety filter, whose repair changed
the coverage by 0.015 and not by 0.1.  The stranding was a defect in the
filter, not a symptom of the policy, and correcting it did not explain the
gap to the reactive heuristic.

### Three measurements that the framework exists to make

1. **On an infeasible instance the metrics mislead.**
   `analysis/infeasible_instance.py` runs the reactive heuristic on the
   report's own N=5 configuration, which the certificate proves infeasible
   for the region: it reaches **CK 0.648** with full connectivity while
   the joint service-continuity metric is **0.000** and the oracle reaches
   0.990 on the twenty sensors. A reader without the certificate would
   read 0.648 as a reasonable controller and 0.000 as a catastrophic one,
   and neither reading would distinguish the instance from a feasible one.
2. **The joint projection holds.**
   `analysis/connectivity_accounting.py` measures the connectivity
   availability step by step: the graph is not left disconnected by a
   move, and the availability below 1.000 is accounted for by UAVs leaving
   the active set. Pinned by a test.
3. **How much of the gap is the rule's privileged access?**
   The `Reactive (local assignment)` arm is the same rule with the global
   coverage state removed, and it turns that caveat into a measurement.

## The paper is generated from the artefacts

`python analysis/assemble_results.py` regenerates every table, fills every
prose token from the same artefacts the tables were read from, replaces the
Results section wholesale, replaces the marked contribution bullet in the
Introduction, and compiles. It **aborts** if any token is left unfilled, so
a missing artefact is a hard error and never a broken paper. No number that
comes from an experiment is typed by hand anywhere in the paper: the audit's
own counts, the size of the test suite and the paper's own limitations are
tokens too.

**The hand-written prose refers to its numbers by MACRO, not by value.** The
macro definitions are written from the token table on every assembly, into
the marked region at the top of the paper:

```
%% BEGIN TOKEN MACROS
\newcommand{\tokGap}{0.276}
...
%% END TOKEN MACROS
```

This matters because the assembler fills a *token* by writing its value
into the source, which consumes the token: the next assembly then has
nothing left to fill, and a number the artefact has changed keeps the
value the first assembly found. Every number in the abstract, the
introduction, the model's parameters, the feasibility section and the
limitations was a candidate for that, and a macro removes the failure.
`analysis/final_checks.py` compares the macros the prose uses with the
ones the token table defines, which is what catches a name that has been
mangled.

Two LaTeX details cost an hour and are worth recording. A control word
ends at the first **non-letter**, so `\tokAltN5R` is the control sequence
`\tokAltN` followed by the characters "5R"; the digits in the macro names
are spelled out. And a macro's body is expanded where it is *used*, so a
token's value that quotes another token has to be resolved before the
definition is written, or the nested token survives into the paper as
literal text.

## The physical layer, and what we do and do not claim

The Python reference PHY and INET's `BreakpointPathLoss` are the same
function: transcribing INET's implementation gives
`PL(d) = l02 + 10*alpha*log10(d/d_bp)`, exactly the log-distance form used
in the report. With the parameters recorded by the OMNeT++ run the two agree
to **0.012 dB** over 24 (distance, exponent) points (`analysis/phy_equivalence.py`).

**We do not claim a runtime cross-validation**, and the reason is measured
rather than asserted. `Simulation/UAV_IoT_Demo/run_phy_probe.sh` sweeps the
UAV's transmit power over 117 dB with receivers at 10, 30, 50 and 80 m:

| TX | 10 m | 30 m | 50 m | 80 m | `minSnir` |
|---|---|---|---|---|---|
| 0.5 W (−3 dBm) | 500 | 500 | 500 | 500 | 46.96 dB |
| 1 mW (−30 dBm) | 500 | 500 | 500 | 500 | 19.97 dB |
| 1 µW (−60 dBm) | 0 | 0 | 0 | 0 | — |
| 1 pW (−120 dBm) | 0 | 0 | 0 | 0 | — |

The control works — the reception count falls from 500 to 0 — and the
`minSnir` statistic tracks the transmit power exactly (27.0 dB for 27.0 dB).
But it does **not** track the receiver distance: the same value is reported
for receivers at 10, 30, 50 and 80 m, although the configured path loss
differs by 13.7 dB between them, and the link-closure threshold is the same
at every distance. The quantity a path-loss cross-validation needs is the SNR
*as a function of distance*, and that is precisely what this statistic does
not report.

The methodological point is the part worth carrying away: a physical-layer
claim that has not been subjected to a negative control is not a measurement.
The first attempt counted MAC frames and reported links closing at 50 km;
the control exposed it.

## Fair-comparison guarantee

Every model runs through the same `SimConfig` with the same seed, sensor
layout, initial UAV positions, batteries, pad locations, failure trace,
episode length and safety constraints. Only the controller differs. The
baselines honour the seed they are given (they previously did not, which
made a five-seed comparison one repeated scene). Vanilla MAPPO is an
*ablation of this codebase's* design, not a claimed reproduction of Yu et
al. — stated as such in the report.

The evaluation of a stochastic controller is **reproducible and paired**:
the sampling stream is seeded from the evaluation seed alone, so every
controller is measured on the same stream on the same scene, and the
component ablation's variants share their training seeds, so their
differences are measured on the same training runs. `analysis/claim_audit.py`
item R1 measures this property rather than asserting it.

\section{The measurement protocol}
Every number in the paper and in this report is produced under one protocol:
\begin{enumerate}[leftmargin=*,label=\textcolor{uavblue}{\bfseries\arabic*.},itemsep=2pt,topsep=2pt]
\item \textbf{Training}: 25 episodes of 2000 control steps per training run. The base comparison trains five runs; the component ablation and the arms train three.
\item \textbf{Evaluation}: five scenes per policy, and the number of evaluation scenes is part of the protocol --- a run with three is a different measurement, because a per-seed row is the mean over the scenes.
\item \textbf{The device and the thread count} are part of the protocol. The floating-point kernels differ between the CPU and the GPU and the order of the reductions differs with the thread count, so two runs of the same configuration that land on different devices are not the same experiment. The device is pinned, the thread count is pinned in code, and every artefact records the device.
\item \textbf{The evaluation is seeded} from the evaluation seed alone, so every controller is measured on the same random stream on the same scene --- common random numbers --- and a comparison between controllers is a comparison between policies rather than between the luck of the draw.
\item \textbf{The ablations are paired}: the variants share the training seeds, so a difference is measured on the same training runs and reported as a confidence interval on the paired difference.
\item \textbf{Inference is by interval, never by threshold}. An explanation is excluded only if the arm that tests it has an upper confidence limit below the gap; a null result is a statement about the resolution of that arm, and the resolution is reported with it.
\end{enumerate}

\section{Negative results, kept on the record}
\begin{itemize}[leftmargin=1.15em,itemsep=4pt,topsep=2pt,label={\color{uavblue}\scriptsize\textbullet}]
\item The \textbf{runtime instrument cannot support a path-loss cross-validation}: a transmit-power sweep shows the available per-receiver SNR statistic tracks the transmit power exactly but is independent of the receiver's distance. The equivalence is therefore established from INET's source, not from a running simulation. This is a negative control that the paper reports on itself.
\item \textbf{Phase 3 (Simu5G PHY) is scaffolded but not executed} with the learned policy.
\item \textbf{The coverage-map summary makes no measurable difference} to the coverage at any resolution tested; it changes what the policy DOES (the swarm's spread), and the paper reports that rather than dropping the feature.
\item \textbf{The thread count does not change the training run} on this workload.
\item \textbf{The reward term for the energy cost is numerically inert} at the reported weights.
\item \textbf{The credit-assignment arm does not resolve the credit assignment}: the cheapest modification in the direction the diagnosis points moves the wrong way, and the paper says so rather than claiming the diagnosis.
\item \textbf{The GPU does not accelerate this workload.} Measured, in \texttt{analysis/\allowbreak{}device\_sensitivity.json}: the GPU takes about 1.26x the CPU's wall clock for the same training run. The profile says why: the simulator is a sequential Python loop and is about 85\% of a run, the network is about 8\% of it, and on the GPU even that 8\% is several times slower in absolute terms (tiny tensors, launch overhead). The measurement is in the artefact, and the earlier claim that the choice "costs about one percent" was false and has been removed from the code and from this file.
\end{itemize}
